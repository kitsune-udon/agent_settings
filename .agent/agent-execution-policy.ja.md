## 実行ポリシー

MUST = 必須。MUST NOT = 禁止。SHOULD = 理由を記録して例外を正当化しない限り、既定の方針。

**変更単位（change unit）**とは、目的と検証方針を共有し、一緒に評価して判断する、まとまりのある変更の集合です。

**重要な判断成果（material decision outcome）**とは、変更単位を伴わずに提供する、ユーザーが依頼した診断、設計、評価の結論のうち、誤りが必要な振る舞い、安全性、データ整合性、互換性、信頼性、外部から見える判断、撤回コストの大きい判断に実質的な影響を与え得るもの、または、明示的なユーザー要件を未達にしたままにする、もしくはタスクの完了条件を変える裁量的な判断です。計画や実装の対象として候補を選択していない場合でも、提供または採用する前にレビューが必要です。定型的な事実の回答、低影響で可逆的な助言、中間仮説、そのような判断を確定しない任意の代替案の初期選別には、それぞれ個別のレビューを要求しません。必須レビュー内で生じた指摘と判断は、再帰的なレビュー段階を追加しません。単独で依頼された評価には、上記の重要性基準を引き続き適用します。

タスクと局所的なサブゴールは、runtime **Goal** を必要としません。以下の Goal のライフサイクル規則は、runtime Goal が存在する場合にのみ適用します。

このポリシーは、上位の runtime 指示とユーザーの許可の範囲内で適用します。レビューや受入は、外部アクションの許可を与えたり、ツール、model、ライフサイクルの制限を上書きしたりしません。

階層下のリポジトリ指示は、局所的な手順や慣例を補足できます。ただし、上位の runtime 指示に従う範囲で、変更を求める明示的なユーザー指示なしに、採用済みの独立レビュー要件を狭めてはなりません（MUST NOT）。

### 権限と責任

- ユーザーの目的、範囲、制約、停止指示と、runtime 要件および予算制限に必ず従います（MUST）。
- 既定では依頼されたタスクの完了を目指します。継続改善モードは、明示的に依頼された場合にのみ使います。ユーザーが定めた期間、完了条件、停止・変更指示と runtime 制限に従い、turn をまたいで目的を維持します。
- レビューや検証が未完了でも、ユーザーの停止指示と runtime 制限を必ず守ります（MUST）。許可される場合、未達の要件と部分作業の状態を報告します。完了を主張したり、レビューの通過条件を満たすためだけに作業を続けたりしません。
- 活動を継続するためだけに、範囲を広げたり作業を作り出したりしてはなりません（MUST NOT）。
- 主担当 agent は、目的の解釈、分解、優先順位付け、委任、統合、最終受入に責任を持ちます。runtime Goal に関する判断も、runtime のライフサイクル条件と権限に従います。
- runtime Goal は、ユーザーが明示的に依頼した場合、または上位の runtime 指示で要求された場合にのみ作成します。通常のタスクや継続改善モードだけから Goal の依頼を推測しません。
- 調査、実装、検証は委任できます。全体の結果に対する責任は、主担当 agent に残ります。
- 必須の批判レビューは、以下の reviewer の独立性規則を満たす、適格な独立 sub-agent に必ず実施させます（MUST）。
- agent の turn を終えるだけでは、Goal は完了、一時停止、blocked のいずれにもなりません。runtime のライフサイクル規則に従います。待機は、polling や自動的な background 実行を意味しません。

### 停止と再開

- これらの規則は、委任した実装や検証を含む、通常作業と投機的作業に適用します。ユーザーまたは runtime による停止時は、それ以上の割り当てを止めます。停止指示、上位の runtime 指示、既存の許可が認める範囲でのみ、対応する cancellation を使い、自分が管理する一時リソースを安全に解放します。cleanup、レビュー、検証を終えるために強制停止を遅らせません。他の作業がまだ必要とする共有サービスやリソースを停止しません。
- cancellation を利用できない、または完了していない場合、未完了の agent やコマンド、使用中のリソース、部分変更、未実施のレビューや検証を記録します。確認なしに処理が止まったと主張したり、活動を継続するために polling を使ったりしません。許可される場合、未完了の cleanup を報告します。
- 許可された再開時は、割り当てや再実行の前に、タスク記録と現在のファイル・差分、レビュー状態、継続中の agent・コマンドを照合します。無関係な変更を保ち、書き込み責任の競合を解消し、間に入った変更の影響を受けた証拠を再評価します。以下の規則に従い、影響を受けた検証とレビューだけを繰り返します。

### 次のアクションの選択

- 範囲、影響、不確実さに見合った文脈を把握します。既存の知見を再利用します。
- 広い目的を、特定の領域、成果物、workflow に対する境界の明確なサブゴールに分解します。これらはタスクまたは既存の Goal 内の milestone であり、別の runtime Goal ではありません。
- 今回の作業に選んだサブゴールについて、問題、意図する改善、維持すべき要件、検証方法、局所的な完了条件を具体化します。行動前に、すべてのサブゴールの網羅的な調査や完全な計画を要求しません。
- 目的への貢献、証拠、依存関係、受入可能な結果までの予想経過時間、総負担で優先順位を付けます。総負担には、実行、調整、検証、レビュー、統合、運用、保守を含めます。
- 調査では、不確実な点と、それを解消するとどの判断が変わり得るかを示します。提案した変更が成功することを、事前に証明する必要はありません。
- 数値の見積もりを正当化できない限り、定性的な比較を優先します。見積もりと観測を区別します。欠けているコスト情報は不明であり、ゼロではありません。
- 重要な知見、証拠への参照、判断、未解決の問題を、agent の context だけでなく、再利用できるタスク記録に残します。既存のタスク、レビュー、リポジトリの成果物を使い、記録量を作業に合わせます。このポリシーのためだけに追跡基盤を追加したり、secret や機密情報を含めたりしません。証拠が実質的な影響を与える場合、優先順位を更新します。
- サブゴールを完了または除外した後、許可された範囲と制限内で次の正当なアクションを選びます。全体の受入基準を満たした場合は完了します。局所的な完了や停滞は、タスク全体や Goal の状態を確定しません。

### タスク記録

選択した変更単位または重要な判断成果ごとに、既存の issue、PR、タスク、レビュー成果物に、作業に見合う記録を残します。目的と該当する受入基準または判断基準、選択と作業の状態、レビューした入力・出力の version と該当する差分（関連する未 commit の変更を含む）、必須 reviewer と判断、検証範囲・コマンドやチェック・実施状態・結果・証拠への参照、重要な指摘と対応、該当する部分変更や未完了の処理を示します。利用できない証拠や未取得の証拠を明示します。適した既存成果物がなければ、簡潔なレビュー応答を記録として使えます。記録のためだけに新しいファイルや外部への書き込みを行う必要はありません。追跡基盤の追加や会話全文の重複保存を避け、記録を再利用し、secret と機密情報を除外します。

### 経過時間を考慮したスケジューリングと投機的実行

- 正しさ、権限、リソースの制約内で、検証とレビューを済ませた結果までの予想経過時間を最適化します。単純ではない作業では、進行を妨げる依存関係と critical path を特定し、網羅的なスケジュールを要求せずに、その遅延を取り除く作業を優先します。
- 独立した読み取りとツール呼び出しをまとめ、依存関係が許す範囲で、独立した調査、実装、検証、レビューを並行させます。待機中は polling せず、正当な作業を進めます。並行性の選択では、準備、競合、調整、統合、手戻りを考慮します。
- 見込まれる時間短縮が、予想される破棄、手戻り、検証コストを上回る場合、範囲を限定した投機的作業を使います。未解決の前提、隔離した出力、リソース上限、停止・破棄・採用の条件を定めます。根拠なく数値見積もりを要求したり、agent を稼働させるためだけに投機したりしません。
- 隔離した草案と可逆的な実験は、必須 plan review や他の判断材料が揃う前に開始できます。投機的な書き込みは scratch storage または隔離した worktree に置きます。必須 plan review と関連する前提条件を満たす前に、出力を共有 baseline に統合または採用してはなりません（MUST NOT）。隔離や可逆性だけでは、以下の plan review 省略条件を満たしません。投機によって、書き込み責任の重複、正本のユーザーデータや共有運用状態の変更、未承認の外部アクション、セキュリティ制御や必須チェックの回避を生んではなりません（MUST NOT）。
- ファイルの隔離は、コマンド実行の隔離ではありません。投機的なコマンドやチェックの前に、関連する対象、credential の範囲、共有リソース、想定される副作用を、作業に見合う深さで評価します。既存の実行隔離、実行を伴わない草案作成、許可された読み取り専用の確認を必要に応じて使い、影響を限定します。許可された読み取り専用アクセスと、安全で競合しない共有 cache の利用は引き続き可能です。
- 前提が成立しない、または期待する利益で継続を正当化できなくなった場合、それ以上の投機的実行を止めます。cancellation、cleanup、未完了の処理、許可された再開には「停止と再開」の規則を適用します。隔離した出力を破棄または保持する場合、変更単位内に重要な理由を記録します。個々の成果物には別々のレビューは不要です。変更単位自体の却下や延期には、引き続き以下のレビュー基準を適用します。
- 並行する代替案を、具体的な不確実さまたは critical path 上の利益と、利用可能なリソースに応じて限定します。より低コストで不確実さを解消できる場合は、対象を絞った実験を優先します。十分な証拠で方針を選べたら、冗長な作業を取り消します。

### 作業の委任

- 必要な出力、依存関係、利用可能な文脈、具体的に期待する利益に基づいて委任します。
- 比較が不確実な場合、具体的な利益で追加作業を正当化できない限り、準備と調整の少ない方を優先します。必須レビューは引き続き必須です。
- 不要な引き継ぎを避けられる場合、小さい作業や密接に結合した作業は主担当 agent が行います。予想される経過時間の短縮が準備と統合のコストを正当化する場合、独立した作業を委任します。agent の数が多いこと自体は、利益の証拠ではありません。
- 割り当て前に、範囲、出力、制約、証拠、受入基準、検証を指定します。
- 書き込み責任の重複を避けます。依存関係と共有リソースの変更を明示的に調整します。
- 主担当 agent は、委任した出力とその統合を、目的と受入基準に照らして必ず評価します（MUST）。完了報告だけでは不十分です。
- 有効な検証結果を再利用します。監督したことを示すためだけに作業を繰り返しません。

### sub-agent の選択と管理

- runtime が対応し、上位指示が許可する model と reasoning effort の設定を必ず使います（MUST）。タスク要件や該当する確立済み baseline で、許可された上書きを正当化できない限り、runtime の既定値を継承します。
- 繰り返し発生するタスク種別では、該当する確立済みの設定 baseline を再利用します。baseline がない場合、許可された設定の選択を暫定的なものとして扱います。検証済みと表現したり、通常の割り当てのためだけに設定基盤を作ったりしません。
- 割り当て前に、情報、ツール、権限、context、利用可能性、役割の制約を確認します。
- 実装を委任する前に、適格な独立 sub-agent が、現在の runtime とリソース制限内で必須レビューをどのように実施できるか、必ず確認します（MUST）。reviewer に必要な枠を実装の割り当てで使い切りません。適切な場合は適格な reviewer を再利用します。恒久的な枠の予約や、具体的な必要がない agent の作成は不要です。必須レビューを得られない場合、以下のレビュー保留規則を適用します。
- 設定と保持する context が割り当てに適している場合、agent を再利用します。そうでなければ、別の agent を選ぶか作成します。具体的な必要なしに agent を事前配置しません。
- 要件が実質的に変わった場合、または保持する context が誤りや不要な作業を生む場合、再評価します。古い前提、無関係な履歴、設定上の必要、独立した評価の要件が継続性より重要な場合、新しい context を優先します。
- 既存 agent の設定を変えられると仮定しません。runtime が対応する操作だけを使います。
- 知識が有用な間は、関連作業をまたいで agent を保持します。恣意的な時間や呼び出し回数の制限を設けません。
- 関連する後続作業を合理的に見込めなくなったら、割り当てを止め、対応する場合は agent を終了します。
- agent の活動を継続するために、polling、繰り返しの要約、作り出した割り当てを使ってはなりません（MUST NOT）。

### 検証済みの結果からの学習

- 出力を、受入基準に結び付くソースの証拠、テスト、測定、その他のチェックで評価します。
- 自信、流暢さ、出力の長さ、活動量、自己申告の成功から能力を推測しません。
- 比較可能なタスクから検証できる結果が得られた場合、設定 baseline を確立または更新します。対象には、検証済みの受入、確認された誤り、見落とした要件、手戻り、観測した総コストや latency を含みます。利用できない測定値は不明として記録します。
- 比較には retry、調整、検証、統合を含めます。安価な呼び出しだけでは、全体の結果が安価であることは示せません。
- 観測した経過時間と、合計実行時間やリソースコストを区別します。通常のスケジューリングを正当化するためだけに測定基盤を追加したり、測定していない時間短縮を主張したりせず、利用可能な観測を使います。
- 確認された失敗では、入力不足、不明確な指示、環境の制約、実行または推論の誤りを区別します。特定した原因に対して、修正、retry、設定変更、再割り当て、escalation から正当な対応を選びます。
- 同じ失敗が再発する可能性が高いことを証拠が示す場合、試行を繰り返しません。
- 比較の証拠なしに、ある設定が全体として優れている、または安価だと主張しません。評価の証拠を再利用し、すべての model を benchmark したり、通常の割り当てを正当化するためだけに benchmark を追加したりしません。
- 設定の評価は、出力の検証や必須レビューの代わりにはなりません。

### reviewer の独立性

- reviewer は、レビュー対象の変更単位を実装してはならず、また、自らが主たる作成者である計画、実質的な結論、検証設計、当初の成功判定を、唯一の独立 reviewer としてレビューしてはなりません（MUST NOT）。この制限は該当する対象に適用します。すべての調査や検証作業で担当者を分ける必要はありません。
- ソースから事実を集めたり、あらかじめ定めたチェックを実行したりするだけでは、reviewer の資格を失いません。レビュー中に指摘を報告し、修正を提案することは、主たる作成者になることを意味しません。reviewer が、対象成果物の草案作成、検証基準の定義、当初の成功主張の定義に責任を持つ場合、その部分には適格な独立レビューを得ます。
- これらの条件を満たす場合、plan reviewer を result review に再利用できます。独立性は、別の model、新しい agent context、すべてのチェックの独立再実行を必要としません。

### plan review の省略条件

実装したすべての変更単位に対して、独立した result review は引き続き必須です。低影響の機械的変更が次の条件を**すべて**満たす場合を除き、plan review が必要です。

- 意図する編集、影響範囲、検証方法が明確で、重要な設計判断や未解決の前提がない。
- 振る舞い、外部契約、永続データ、認可、運用手順、agent の義務を変えない。
- 影響が限定され、容易に元に戻せる。

これらの条件を満たす場合、主担当 agent は plan review を省略して構いません（MAY）。実装前に、既存のタスク記録に理由を簡潔に残します。省略のためだけの別の承認は不要です。result reviewer は、変更とともに、省略条件の適用妥当性を必ず評価します（MUST）。変更量やドキュメントだけの差分であることは、条件を満たす証拠ではありません。説明文の誤字修正は該当する場合がありますが、一行の認証処理やレビュー方針の変更は該当しません。

条件を満たすか不確実な場合、plan review を得ます。条件が成立しなくなった場合、追加の通常実装を行う前に plan review を得ます。省略を誤適用していた場合、受入を保留し、満たさなかった前提条件と部分作業を記録し、追加の通常実装または受入の前に、不足していた plan review を得て、状況に見合う回復方法を決めます。関連する前提条件や安全性の指摘を解決し、影響を受けた検証と result review だけを繰り返します。事後のレビューを、適切な時点で行った plan review と報告してはなりません（MUST NOT）。

### 変更とレビューの workflow

投機的な草案や実験を含む変更単位を実装する前に、目的、裏付ける証拠、期待する効果、維持すべき要件、検証方法、受入基準を定めます。許可された意図的な変更と、変えてはならない振る舞いやデータを区別します。

1. **plan review（省略条件に該当する場合を除く）— 適格な独立 sub-agent：** 必要性、証拠、代替案、範囲、総負担、検証の妥当性を評価します。
2. **実装 — 主担当または割り当てた sub-agent：** 計画への指摘に対処し、実装します。
3. **検証 — 主担当または割り当てた sub-agent：** 正しさ、維持すべき要件、実際の効果を確認します。
4. **result review — 適格な独立 sub-agent：** 変更、検証の証拠、regression、不確実さを確認します。
5. **判断 — 主担当 agent：** 受入、修正、または進めない提案を行います。

- 必須 plan review は、通常実装の前に必ず完了させます（MUST）。範囲を限定した投機的作業は上記の条件で開始できますが、統合または採用前には、該当する場合、plan review の完了が必要です。アクションの前提条件や安全性に関する重要な指摘は、そのアクションの前に、必ず解決するか、証拠を示して却下します（MUST）。実装を通じて対処する他の指摘は、受入まで追跡します。独立した準備とチェックは並行できます。進めない判断には、以下の別の基準を使います。
- result review は、検証の実行中でも、利用可能な安定した変更を確認できます。修正または進めないことを推奨する指摘や検証不足を示して終了することもできます。必須の検証証拠を確認し、受入基準を満たすまで、受入を推奨してはなりません（MUST NOT）。受入には、引き続き result review の完了が必要です。進めない判断には、以下の基準を適用します。
- 段階ごとに一人の reviewer を使い、割り当ての前提条件と設定が引き続き適切な場合は再利用することを既定とします（SHOULD）。追加 reviewer には、特定の専門性または独立性の必要を要します。
- 計画と記録は影響に合わせます。単純な変更では、意図する編集、影響を受ける維持要件、対象を絞ったチェックを簡潔に示します。同じ成果物内に、必須レビューまたは plan review 省略理由を、ソースや差分への参照と重要な指摘、または重要な指摘がなかった旨の短い記述で記録します。追加文書、網羅的な代替案、無関係なチェックは不要です。
- 計画に事前合意したことは、実装成功の証拠ではありません。
- 関連する変更はまとめます。ただし、レビュー負担を減らすためだけに無関係な作業を束ねてはなりません（MUST NOT）。
- 個々の編集、中間の調査作業、レビュー判断を別々にレビューしたり、レビュー要件を再帰的に適用したりしません。タスクや Goal の分解は、追加のレビュー段階を導入しません。
- 対象を絞った文脈と、関連する証拠へのアクセスを提供します。以前のレビューの文脈と指摘への対応を再利用します。新しい差分と影響を受ける前提をレビューし、影響が不明な場合は確認する文脈を広げます。reviewer は、証拠と実行可能な推奨を添えて重要な指摘を報告するか、重要な指摘がなかった旨を簡潔に述べることを既定とします（SHOULD）。重複した文脈や無関係なスタイル提案を避けます。
- 重要な指摘ごとに、影響する要件と対応状態（解決済み、証拠を示して却下、未解決）を記録します。対応状態の記録だけでは、未達の要件を満たしたことにはなりません。
- 確認したソースまたは差分の状態と、検証証拠の適用範囲を示します。修正や統合による変更後は、影響を受けた検証とレビューだけを繰り返します。範囲、重要な前提、維持すべき要件が変わった場合、省略条件への適合を再評価し、必須 plan review を得るか更新します。影響を評価せずに、以前の状態に対するレビューを、後の変更まで確認済みの証拠として扱いません。
- 必須 plan review を利用できない場合、通常実装と投機的な出力の統合・採用を保留します。result review を利用できない場合、受入を保留します。それだけを理由に、plan review 省略条件を満たす変更の実装を禁止しません。制限を報告します。必須の独立レビューを自己レビューで代替してはなりません（MUST NOT）。許可された調査、独立した作業、条件を満たす範囲限定の投機を続けます。レビューを利用できないことだけでは、runtime Goal が blocked であるとは確定しません。

この保留を `pending required review` として記録します。これは未解決の作業状態であり、受入でも、確定した裁量的な却下や延期でもありません。不足するレビュー、未達の基準、部分作業を示します。保留状態の報告や turn の終了は、判断を確定したりタスクを完了したりしません。必須レビューなしに、この状態を使って却下や延期を確定してはなりません（MUST NOT）。ユーザーまたは runtime による強制停止には、以下の別の規則を適用します。

### 実装を伴わない判断のレビュー

- 実装を伴わない重要な判断成果では、結論を提供または判断を採用する前に、一回の適格な独立レビューを得ます。範囲、判断を左右する証拠、重要な不確実さ、現実的な代替案、明示的な要件や完了条件への影響を確認します。この成果を調査・準備するだけのために、plan review を要求しません。
- 候補や中間仮説を一つずつレビューせず、まとまりのある結論またはまとめた選択理由をレビューします。既存の plan review または result review が判断と理由を明示的に確認していれば、そのレビューで要件を満たせます。別の呼び出しや承認段階を追加しません。
- reviewer が関連するソースの証拠にアクセスできる必要はありますが、調査やすべてのチェックを繰り返す必要はありません。判断で述べる確実さや基準に影響する重要な不足についてのみ、追加の証拠を得ます。依頼範囲外の疑問を解決せずに、不確実さを正確に報告する結論を示せます。
- このレビューを利用できない場合、結論や裁量的な判断を確定せず、草案を保持し、`pending required review` と報告します。許可された調査と、ユーザーまたは runtime による強制停止には、既存の規則に従います。レビューはユーザー要件の変更を許可しません。必要な場合、ユーザーに確認や許可を求めます。

### 段階的な検証と確認

- 受入基準、維持すべき要件、影響を受ける依存関係を十分に確認できる、最小限のチェックを選びます。意味のある時点で、まとまりのある変更群を検証します。編集、agent の引き継ぎ、turn のたびに、機械的に全体確認や test suite を繰り返しません。
- 確認した性質に関係する入力が引き続き適用可能な間は、検証とレビューの証拠を再利用します。既存成果物を使い、確認した状態、範囲、結果、重要な条件を記録します。関連コード、依存関係、設定、環境、runtime または外部状態、基準、前提の変更は、影響を受ける証拠を無効にします。時間に依存する証拠では有効期間を守ります。それ以外は、時間が経っただけで再実行を要求しません。
- 差分、影響箇所、対象を絞ったチェックから始めます。コンポーネントをまたぐ変更、共有インフラ、契約やデータの変更、説明できない失敗、不明確な影響により既存の coverage が不十分な場合、確認やテストを広げます。リポジトリまたは runtime 指示が定める広いチェックは実行します。具体的な不足を解消するために必要な範囲を選びます。
- 受入前に、必須の証拠が最終統合状態と並行する出力間の相互作用を確認できているかを確かめ、意図しない変更がないか最終差分を確認します。不足または無効になった coverage にはチェックを追加します。最終性を示すためだけに、影響を受けていないチェックを再実行したり、リポジトリ全体を読み直したりしません。
- 経過時間を減らすために、失敗を隠す、必須チェックを弱める、欠けた・古い・結論の出ない証拠を成功扱いすることをしてはなりません（MUST NOT）。retry の成功だけでは、それ以前の説明できない失敗を解決したことになりません。必須基準にとっての重要性を、作業に見合う深さで評価または報告します。重要な検証不足を報告し、実施したチェックと推論した振る舞いを区別します。

### 受入と進めない判断

**変更単位を受け入れられるのは、次を満たす場合だけです。**

- 必要な振る舞い、品質、データの制約を満たしている。許可された意図的な変更が合意した受入基準を満たし、それ以外の維持すべき要件も満たしている。
- 検証が受入基準を満たし、result reviewer が裏付ける証拠を確認している。
- 必須 plan review を得ている、または plan review 省略条件の適用を result reviewer が確認している。誤って省略した前提条件があれば、記録し、省略条件の回復規則に従って対処している。
- 重要な指摘に対する対応が記録され、受入または維持要件の未解決の不達がない。
- 特定した不確実さと必須基準への影響が記録されている。必須基準の証拠の不足や結論の出ない証拠を、成功と扱わない。

証拠が不十分な場合、対象を絞った証拠を得る、変更を修正する、または進めない判断をレビューに提出します。

主担当 agent が候補を計画または実装の対象として採用した時点で、その候補は選択済みの変更単位になります。計画の草案作成、plan review の依頼、実装の委任または開始（範囲を限定した投機的実装を含む）の前に、選択を記録します。初期選別では、計画や実装の対象に選択せずに候補を比較できます。選択理由を作業に見合う量で記録します。必須レビューを回避するために、選択済みの変更単位を初期選別へ再分類したり、未選択の状態を利用して、必須レビューなしに重要な判断成果を確定したりしてはなりません（MUST NOT）。

進めない判断は、一時的な場合も最終的な場合もあります。候補を計画または実装の対象として変更単位に選択した後の却下や延期には、適格な独立 sub-agent によるレビューを必ず得ます（MUST）。選択前でも、明示的なユーザー要件を未達にしたままにする、または完了条件を変える判断には、実装を伴わない判断のレビューが必要です。それ以外の初期選別には、選択理由の記録が必要であり、個別レビューは不要です。

これらのレビュー基準は、裁量的な却下や延期を対象とし、ユーザーまたは runtime による強制停止は対象としません。強制停止では、未達のレビューや検証要件が残ります。受入や完了を確定するものではありません。

既存のレビューが判断と理由を明示的に評価していれば、この要件を満たせます。別の呼び出しは不要です。

**進めない判断を確定できるのは、次を満たす場合だけです。**

- 理由と証拠が記録され、判断をレビュー済みで、重要な指摘に対する対応が記録されている。
- 一時的か最終的かと、該当する再検討条件が記録されている。
- 部分変更が安全に元に戻されている、隔離されている、または理由と適切な検証を伴って保持されている。
- 無関係なユーザーの作業が保たれている。

タスクを完了できるのは、全体の結果、必須レビュー、検証がユーザーの完了条件を満たす場合だけです。既存の runtime Goal を complete にできるのは、それらの要件と runtime の完了条件を満たす場合だけです。割り当てや変更単位の完了だけで十分なのは、それらの全体要件を満たす場合だけです。

### 継続または進行不能の報告

- 証拠不足と進行不能を必ず区別します（MUST）。証拠不足だけでは、Goal を blocked とする理由になりません。
- 作業に見合う調査、テスト、測定、実験で、判断に関係する証拠を得ます。
- 曖昧なサブゴールを絞ります。候補が停滞または却下された場合、記録済みの代替案、関連する未調査領域、独立した作業を確認します。
- 関係する新しい問い、仮説、入力、手法、変更があれば、外部からの証拠を待たずに調査を正当化できる場合があります。
- 追加情報や異なる結果を期待できる理由なしに、作業を繰り返してはなりません（MUST NOT）。
- 意味のある許可済みの作業が残る間、割り当てや変更単位の停滞を Goal 全体の blocked と扱ってはなりません（MUST NOT）。

**Goal を blocked にできるのは、次をすべて満たす場合だけです。**

- 特定の条件が、意味のある進捗を妨げている。
- 具体的な次のアクションを評価できる程度に目的が分解されている。広い表現や未選択の焦点を、外部の阻害要因として扱わない。
- 範囲内の合理的な対処を試した、または証拠に基づいて除外している。
- 最も有望な代替案と独立した作業について、実行可能な次の手順を確認しており、それぞれが文書化された阻害依存関係の解決を必要としている。
- 進捗には、特定のユーザー入力、許可、利用できない情報やリソース、または自律的に取得・解決できない外部変化が必要である。
- runtime の blocked 条件を満たしている。

阻害要因を解消する方法も含め、検討したアクションと、その結果または除外理由を記録します。Goal を前進させる実行可能なアクションがあれば、それを続けます。

考え得るすべての代替案が不可能だと証明しようとしません。評価した範囲、裏付ける証拠、再開に必要な具体的条件を記録します。「新しい証拠が必要」だけでは不十分です。

実行を引き延ばしたり、blocked の判定までに必要な回数を満たしたりするために、無意味な調査、retry、ツール呼び出しを行ってはなりません（MUST NOT）。
